# 專案與產品價值評估模型 (Project & Product Assessment)

## 1. 產品評估七大維度
1. **功能定位清晰度**：專案核心目標是否單一且明確？是否避免過度複雜化？
2. **現場痛點真實度**：是否真正解決工作現場的真實困難與效率瓶頸？
3. **核心功能完整性**：關鍵工作流程是否已閉環？有無阻塞性殘留？
4. **開源軟體參照度 (OSS Matrix)**：外部生態是否有現成或更優解答？
5. **差異化與獨特性**：本專案對比通用方案，是否具備離線隱私、公務對齊或特定工作流優勢？
6. **實用性與易用性**：啟動門檻是否夠低？能否秒開或一鍵免安裝？
7. **維護與演進成本**：相依套件是否過重？日後維護是否需要持續高成本介入？

## 2. 開源軟體 (OSS) 三級參照
- **Direct Competitor（直接競品）**：功能重疊度高，評估是否有不可取代的本機離線或專用工作流價值。
- **Partial Reference（局部參照）**：在架構、演算法或特定體驗上可作為實作借鑒。
- **Technical Reference（技術參照）**：提供基礎底層技術、協定或引擎支援。

## 3. 六大處置出口 (Disposition Decisions)
- **Build**：自主開發並維持高度客製。
- **Build + Reference**：自主開發並積極借鑒外部優秀開源架構。
- **Adopt + Extend**：基於成熟開源方案二次擴充。
- **Adopt**：直接採用現成成熟工具，專案轉為串接或薄封裝。
- **Freeze**：功能完整且穩定，進入凍結維護期，不再新增大型特性。
- **Archive**：價值已完全轉移或被淘汰，進行封存。

## 4. 依需求選用技術設計參考

- **適用範圍**：大型新專案、跨模組功能、架構調整，或涉及資料格式、API 合約、安全與復原的重大取捨時，依尚未解決的問題選用外部參考。一般 Bug、局部修改、測試、Build、Release 與版本管理不強制研究或新增設計文件。
- **候選來源**：[Design Docs](https://www.designdocs.dev/) 用於尋找真實 Design Docs／RFC，引用時追溯原始專案文件；[Atlassian 設計文件指引](https://www.atlassian.com/work-management/knowledge-sharing/documentation/software-design-document/) 用於必要章節結構。清單不是必查項目，優先採專案既有文件與技術官方文件。
- **選用補充**：需要文件範本時可參考 [software-doc-templates](https://github.com/Milkeles/software-doc-templates)；需要探索架構模式時可參考 [awesome-software-architecture](https://github.com/mehdihadeli/awesome-software-architecture)，再核對原始資料。範本與精選清單不等於已驗證的實作案例，不因參考大型公司的系統而引入微服務、分散式架構或大型框架。

### 本工作區的選擇重點

| 需求類型 | 優先釐清的設計問題 |
|---|---|
| 行政文件、影像與批次資料工具 | 原始資料保護、格式與編碼、預覽／確認、重複與衝突、部分失敗處理及復原 |
| Windows 桌面與 Portable 工具 | 啟動與相依環境、背景任務與取消、進度回報、高 DPI、無管理者權限及跨電腦使用 |
| 輕量 Web、手機適配與家庭／個人工具 | 儲存與資料一致性、帳號及權限邊界、跨裝置操作、離線限制；維持足以滿足需求的簡單架構 |

- **最小決策紀錄**：依任務需要，在既有規劃文件、ARCHITECTURE 或 MEMORY 中記錄問題與限制、可行方案、採用理由與代價、受影響的資料／介面邊界及驗證方式；不重複建立文件，也不要求填滿所有範本章節。
- **可核對性與停止條件**：記錄原始來源網址及借鑑項目，必要時固定版本／Commit；無法存取時如實說明，不虛構研究或繞過限制。足以解決本次決策與驗證需求後停止研究，不因更多範本或新架構延後已通過門檻的交付。

## 5. Agent 引導式需求探索與產品決策規範

### 5.1 適用範圍
- 適用於：
  - 尚未開始開發的新專案
  - 已完成部分功能的專案
  - 已具備完整操作流程的產品
  - 接近發布的成熟專案
  - 已發布並進入維護階段的產品
- 使用者可在任何開發階段要求 Agent 協助重新檢視產品方向。
- 需求探索不代表必須新增功能、全面改版或重新進入開發階段。

### 5.2 啟動條件
- 當使用者明確提出下列或相近需求時，進入產品探索模式：
  - 幫我規劃產品
  - 幫我探索適合的方向
  - 透過問卷引導我
  - 幫我重新評估這個專案
  - 我還不確定產品應該怎麼設計
  - 幫我討論功能、操作及產品細節
  - 開啟產品探索模式
- 若需求已經明確，或使用者要求直接修改、製作、測試、發布，不強制啟動問卷。

### 5.3 既有專案先理解現況
- 既有專案開始探索前，應先讀取可取得的 Repository、核心功能、主要 UI、相關文件及有效設計決策，確認：
  1. 目前產品定位
  2. 既有功能與操作流程
  3. 已完成及未完成項目
  4. 現有 UI／UX
  5. 使用者已確認需求
  6. 已知限制及主要問題
  7. 目前成熟度與發布狀態
- 不得只根據專案名稱或過往印象自行推測功能。
- 不得忽略現有成果，直接以新專案方式重新規劃。

### 5.4 動態問卷設計
- 依專案性質與實際需要設計問題，訪談可涵蓋：產品定位、目標使用者、核心功能、使用情境、操作流程、UI／UX、視覺風格、技術選型、資料管理、安全與隱私、開發優先順序、維護及發布方向。
- 不必每個專案都詢問全部項目；問題應具實際決策價值，不為增加問卷題數而加入無關問題。
- 可依需要每輪提出約 3～5 題；若只有一個關鍵問題，直接詢問即可。
- 應根據使用者答案動態調整後續問題，不使用無法調整的固定長問卷。

### 5.5 問卷回答自由度
- 所有選項式問題均允許使用者自行提出不同答案。依題目性質支援：
  - 單選、複選、自由文字輸入、預設選項搭配補充說明、其他／自行輸入、尚未決定、由 AI 建議、跳過、修改先前答案。
- Agent 的預設選項只是協助使用者思考，不得限制需求範圍。
- 使用者自行輸入的內容優先於預設選項；若提出不同於選項的構想，應理解並納入後續分析，不得強制歸類為原本的選項。

### 5.6 Agent 的主動分析責任
- Agent 不只是收集答案，應主動：
  - 分析需求合理性、發現需求衝突、比較不同方案、指出不必要的功能、評估現有架構相容性、必要時研究成熟產品與開源案例、說明開發及維護成本、提供有依據的建議、區分已確認需求與 AI 推論。
- 不得一味附和使用者；若維持現況比改版更合理，應直接提出。

### 5.7 訪談結束條件
- 當主要需求已足以判斷產品方向，或使用者要求停止訪談時，結束提問。
- 不得為追求完整問卷而無限延長討論。

### 5.8 產出產品方向決策摘要
- 訪談完成後，整理以下 11 項決策摘要：
  1. 產品定位
  2. 現有功能與操作流程
  3. 已確認需求
  4. 建議保留的功能
  5. 建議修改或新增的功能
  6. UI／UX 設計方向
  7. 技術與資料限制
  8. 本次不處理的項目
  9. 建議產品發展方向
  10. 必要的開發階段與驗收條件
  11. 尚未確認的事項
- 既有專案應額外判斷：
  - **維持現況**｜**局部改善**｜**功能擴充**｜**重大改版**｜**暫不決定**
  - 不得預設重大改版優於維持現況。

### 5.9 執行邊界
- 探索模式預設僅進行研究、分析、訪談與整理。
- 未經使用者明確要求，不修改 Repository、不重構、不 Commit、不 Push。
- 探索成果不得自動覆寫既有正式規格。
- 使用者明確要求開始製作時，依目前已確認的需求轉入執行模式，不重新啟動問卷。
