# Agent 執行規範與停止條件 (Agent Execution)

## 1. 核心開發原則
1. **先讀後改**：先讀取專案架構與前次 HANDOFF 狀態，再行修改。
2. **最小修改**：聚焦單一任務，不隨意重構無關模組。
3. **功能相容**：維護既有功能完整性，不破壞原本正常運作的能力。
4. **真實驗證**：完成修改前必須透過工具或指令進行實際驗證，嚴禁虛構測試數據。

## 2. 三級問題分類與停止條件
- **阻斷性問題（必須處理）**：程式無法執行、核心功能失效、資料毀損遺失、明確安全隱患。
- **重要問題（當次修正）**：高機率誘發異常、重度效能瓶頸、已重現之明確 Bug。
- **改善建議（不得阻礙交付）**：架構再抽象化、最新語法或框架升級、微小視覺偏好、假設性極限邊界。
- **停止條件**：當使用者目標達成、核心功能正常、測試與實測通過、無阻斷性重大問題時，即判定「目前版本可交付」，立即停止擴大修改。

## 3. UI／UX 真實案例參考原則

### 適用時機與候選來源
- 新專案介面設計、使用者明確要求 UI／UX 改善、手機版／桌面版／響應式介面調整，或主要操作流程有明確 UX 問題時，依需求尋找相似的真實產品案例。
- 一般 Bug 修正、測試、Build、Release、版本管理及其他非 UI 任務，不強制執行設計案例研究。
- 優先選用可免費公開瀏覽的案例：[Banani](https://www.banani.co/references)、[Refero](https://refero.design/)、[Design Spells](https://designspells.com/)；視需要補充 [Screenlane](https://screenlane.com/)、[UI Sources](https://www.uisources.com/)、[Mobbin](https://mobbin.com/)。
- 上述網站是候選來源，不是逐一查詢清單；依任務選擇適合來源與可存取內容，不要求購買付費方案。

### 選擇與運用方式
1. 先檢查目前專案的實際介面、核心功能與操作流程；新專案依已確認需求建立基線。
2. 依使用情境選擇相似的真實產品，優先研究資訊層級、導覽結構、操作步驟與互動設計。
3. 視需要借鑑卡片、工具列、底部導覽、彈出面板等元件，不直接複製整個產品介面。
4. 不為視覺效果增加不必要的功能、設定或操作步驟。
5. 手機與桌面可採不同版面，但應維持既有功能、資料及業務規則一致。
6. Windows 桌面工具優先考慮原生操作習慣與使用效率，不強制採用手機 App 設計模式。

### 來源真實性與存取限制
- 引用外部案例時，提供實際產品或案例名稱、可核對的來源網址、參考的 UI／UX 元素，以及適合目前專案的原因。
- 不得虛構案例或截圖、把概念作品描述成已上線產品，或在未實際取得資料時宣稱已完成研究。
- 不得繞過登入限制、付費牆或其他存取限制。若來源無法存取，應如實說明，並可使用現有專案畫面、使用者提供的截圖或其他可驗證資料繼續工作。

### 與既有任務分類整合
- **AUDIT／EVALUATE（檢查／分析）**：可研究真實案例、提出設計比較與改善建議；本類任務不修改 Repository。
- **FIX／IMPROVE（修正／改善）**：先確認修改前基線，僅實作本次明確要求的介面範圍，維持原有功能及資料相容性；完成相關測試、操作驗證與 `git diff` 檢查。
- **RELEASE／結案**：UI 美化不得自動成為發布前必要項目；Release Gate 已通過時，不因更漂亮的介面延後發布。非必要 UI 改善列入後續觀察，沿用既有問題分級與停止條件。
