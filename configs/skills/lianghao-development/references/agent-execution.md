# Agent 執行規範與停止條件 (Agent Execution)

## 1. 核心開發原則
1. **先讀後改**：先讀取專案架構與前次 HANDOFF 狀態，再行修改。
2. **最小修改**：聚焦單一任務，不隨意重構無關模組。
3. **功能相容**：維護既有功能完整性，不破壞原本正常運作的能力。
4. **真實驗證**：完成修改前必須透過工具或指令進行實際驗證，嚴禁虛構測試數據。

## 2. 三級問題分類與停止條件
- **阻斷性問題（必須處理）**：程式無法執行、核心功能失效、資料毀損遺失、明確安全隱患。
- **重要問題（當次修正）**：高機率誘發異常、重度效能瓶頸、已重現之明確 Bug。
- **改善建議（不得阻礙交付）**：架構再抽象化、最新語法或框架升級、微小視覺偏好、假設性極限邊界。
- **停止條件**：當使用者目標達成、核心功能正常、測試與實測通過、無阻斷性重大問題時，即判定「目前版本可交付」，立即停止擴大修改。

## 3. UI／UX 自主風格探索、開源參考與驗證原則

### 3.1 設計前先研究與候選來源
- 當任務涉及全新 UI、整體視覺改版、明確 UI／UX 改善、手機版／桌面版／響應式介面調整或重大操作流程調整時，應先理解產品用途及使用情境。
- 不得在沒有設計分析的情況下，直接套用通用 AI 生成介面。
- 應優先研究：
  - 成熟軟體產品
  - GitHub 開源 UI 專案
  - 現有遊戲介面
  - 適合的設計系統
  - 實際可使用的 UI 元件
- 原則上比較 **2～3 個**真正適用的案例或設計方向，並提供可查證的來源。
- 一般 Bug 修正、測試、Build、Release、版本管理及其他非 UI 任務，不強制執行設計案例研究。
- 優先選用可免費公開瀏覽的案例：[Banani](https://www.banani.co/references)、[Refero](https://refero.design/)、[Design Spells](https://designspells.com/)；視需要補充 [Screenlane](https://screenlane.com/)、[UI Sources](https://www.uisources.com/)、[Mobbin](https://mobbin.com/)。
- 上述網站是候選來源，不是逐一查詢清單；依任務選擇適合來源與可存取內容，不要求購買付費方案。

### 3.2 依操作需求補充參考

| 需求 | 優先參考與判斷重點 |
|---|---|
| 行政／資料工具的表單、搜尋、篩選與列表 | [UI-Patterns](https://ui-patterns.com/) 的互動模式解說，搭配實際產品案例；優先減少輸入錯誤、重複操作與資訊查找成本 |
| 匯入、預覽、確認、批次處理與匯出 | 選擇相似工作流程，研究進度、取消、部分失敗、衝突處理及結果摘要；維持原始資料保護與可復原性 |
| Windows 桌面工具 | 先核對原生操作習慣、鍵盤效率、視窗與高 DPI 行為，並依既有 `windows-tool-ux` 規範；避免為模仿手機畫面而隱藏常用操作 |
| 手機／響應式、多步驟或新手引導 | 既有真實案例來源，必要時補充 [Page Flows](https://pageflows.com/) 的連續流程資料；研究觸控、返回、輸入與狀態保留，不憑單張截圖推測完整流程 |
| 明確要求付費、結帳或商業轉換改善 | 可選用 [GoodUI](https://goodui.org/) 的實驗資料；核對測試情境、指標、樣本與限制，不直接套用他站成效，不為非商業工具新增行銷或付費流程 |
| 遊戲介面、HUD、系統狀態機與微互動（本機／Web） | 載入 `game-design` Skill；介面分類參考 [Game UI Database](https://gameuidatabase.com/)、動態轉場參考 [Interface In Game](https://interfaceingame.com/)、手遊排版參考 [GameUI Net](https://gameui.net/)；Web 網頁遊戲參考 [Poki](https://developers.poki.com/)、[CrazyGames](https://developer.crazygames.com/) 與 [Itch.io](https://itch.io/games/html5)，遵循 Safe Frame、抽屜式面板、情境 HUD 與首屏 15MB 限制；工具軟體套用遊戲風格 UI 另依下方第 4 節辦理 |

### 3.3 自主風格探索與避免制式 AI 介面
- **使用者未指定風格**：應根據產品定位、主要操作、使用者類型、平臺與螢幕尺寸、功能及資訊密度、現有設計、開發與維護成本，自主探索適合的視覺方向（可包含專業工具、簡約、工業、科技、復古、手繪、遊戲、擬物及其他風格），不預設任何單一風格為最佳選擇。
- **使用者指定風格**：若使用者已指定視覺風格、參考圖片、特定產品、按鈕或元件形式、介面互動方式，應以指定方向優先。Agent 可提出不適用的部分及原因，但不得無理由改成其他慣用風格。
- **避免制式 AI 介面**：不得無理由大量使用：
  - 相似的圓角卡片
  - 大面積漸層背景
  - 裝飾性陰影
  - 過多彩色圖示
  - 沒有實際用途的浮動面板
  - 過度寬鬆的資訊排列
  - 以上元素並非禁止使用，而是必須符合產品的功能與設計目的。

### 3.4 選擇運用與來源真實性
1. 先檢查目前專案的實際介面、核心功能與操作流程；新專案依已確認需求建立基線。
2. 依使用情境選擇相似的真實產品或開源專案，優先研究資訊層級、導覽結構、操作步驟與互動設計。
3. 視需要借鑑卡片、工具列、底部導覽、彈出面板等元件，不直接複製整個產品介面。
4. 不為視覺效果增加不必要的功能、設定或操作步驟。
5. 手機與桌面可採不同版面，但應維持既有功能、資料及業務規則一致。
6. Windows 桌面工具優先考慮原生操作習慣與使用效率，不強制採用手機 App 設計模式。
- **資料類型須區分**：真實產品畫面／流程用於觀察既有行為；UI-Patterns 等模式解說用於分析設計理由；文件範本只提供結構；A/B 測試僅支持特定條件下的實驗結果。產品已上線或知名，不代表其設計已證明適合目前專案。
- **來源真實性與存取限制**：引用外部案例時，提供實際產品或開源案例名稱、可核對的來源網址、參考的 UI／UX 元素，以及適合目前專案的原因。不得虛構案例或截圖、把概念作品描述成已上線產品，或在未實際取得資料時宣稱已完成研究。不得繞過登入限制、付費牆或其他存取限制；若無法取得外部資料應如實說明，並使用現有專案畫面、使用者提供的截圖或其他可驗證資料繼續工作。

### 3.5 UI／UX 驗證標準
- 不能只以美觀程度判斷設計成功，應綜合評估：
  1. 主要功能是否容易找到
  2. 按鈕用途是否清楚
  3. 操作狀態是否容易辨識
  4. 功能分區是否合理
  5. 使用者是否容易知道下一步
  6. 是否增加操作步驟
  7. 資料及文字是否容易閱讀
  8. 不同解析度與 DPI 是否正常
  9. 鍵盤、滑鼠及觸控是否符合使用情境
  10. 是否影響效能與穩定性
- 可用實際操作情境進行驗證，不將靜態預覽圖視為已完成 UX 測試；未量測時不得宣稱效率、轉換率或滿意度提升的數字。

## 4. 遊戲風格工具 UI 設計與選型規範

### 4.1 核心定位
- **遊戲風格 UI 不等於 Q 版 UI**。不同遊戲類型具有不同的操作結構與美術表現。
- 本規則的目的是借鑑遊戲介面在功能分區、操作暗示、資訊層級及互動回饋方面的優點，改善工具型產品。
- **遊戲風格介面不代表將工具軟體的業務功能遊戲化。**

### 4.2 遊戲類型與美術風格分開選擇
- **遊戲類型**：例如 RPG、MMORPG、策略遊戲、經營模擬、戰術遊戲、冒險遊戲、休閒遊戲、科幻控制類遊戲。
- **美術風格**：例如 Q 版、寫實、日系動漫、像素、手繪、奇幻、工業、機械、賽博龐克、復古、擬物。
- 遊戲類型與美術風格可以自由組合；不得將所有遊戲風格預設為 Q 版、木質 RPG、羊皮紙或卡通介面。

### 4.3 自主設計選型
- 當使用者只要求「遊戲風格 UI」而未指定具體形式時，Agent 應研究符合專案特性的設計。
- 重大改版原則上提出 **2～3 種**具有實質差異的方向，分析：視覺特色、按鈕設計、面板結構、導覽方式、字體與圖示、操作回饋、資訊密度、技術可行性、維護成本。
- 推薦最適合的一種，而不是直接選擇最華麗的風格。
- 若使用者已指定風格，則直接依指定方向進行研究，不重複選型。

### 4.4 保留工具軟體本質
- **可遊戲風格化的元素**：按鈕、工具列、分頁、面板、狀態標籤、進度條、圖示、導覽、對話框、適當的互動動畫。
- **不得自行加入**：等級系統、經驗值、成就獎勵、虛擬貨幣、無需求的遊戲角色、劇情任務、不必要的操作步驟、強制動畫與音效。
- 原有功能名稱應保持清楚；不得為了遊戲氣氛，將新增、刪除、設定、匯出、開始、停止等功能改成難以理解的遊戲術語。

### 4.5 視覺與互動原則
- 遊戲風格 UI 應優先強化：
  1. 明確的功能分區
  2. 容易辨識的按鈕
  3. 主要與次要操作的區別
  4. 清楚的執行狀態
  5. 明確的選取與焦點
  6. 一致的互動回饋
  7. 易讀的文字與數字
  8. 適當的畫面資訊密度
- 裝飾性元素不得干擾實際工作；動畫不得明顯增加操作等待時間或資源消耗。

### 4.6 預覽圖與實作分離
- 使用者要求 UI 預覽時，應先依實際 Repository、現有功能與操作流程產生概念圖，不得僅根據專案名稱生成通用或無關的遊戲畫面（例如：`auto-learning-bot` 是公務研習自動化工具，不應被設計成一般學生的每日打卡或學習積分系統）。
- 概念圖若包含新功能或不同的操作流程，應標示為設計提案。
- **使用者只要求預覽圖時，不修改程式、不新增功能、不改變正式規格。**

### 4.7 各專案保有自己的特色
- 不同 Repository 可以共用設計語言（如按鈕、狀態提示、元件規範及互動原則），但不應強迫不同用途的產品使用相同的美術主題。
- 適用方向舉例（非各專案必須採用的正式設計，具體風格仍由使用者需求及實際產品特性決定）：
  - PDF 工具可以參考 RPG 文件工坊
  - Desktop Fence 可以參考遊戲倉庫介面
  - 精油配方可以參考合成與製作系統
  - 訂閱管理可以參考遊戲式行事曆
  - `auto-learning-bot` 可以參考遊戲控制中心

### 4.8 成熟專案的改版限制
- 既有成熟產品應先確認功能、測試、Build、版本及發布狀態。
- 若只需要修改視覺元件，不應全面重構核心架構，亦不得為了遊戲風格自行更換技術棧。
- 已達發布標準的產品，不因非必要美術改善而延後發布；遊戲風格 UI 可以作為獨立改版需求或後續版本。

## 5. Agent 任務分類與執行邊界

- **A. 檢查任務（`AUDIT`）**：唯讀檢視 Git 狀態、測試、安全與設計案例比較，提出改善建議；本類任務不修改 Repository。
- **B. 修正／改善任務（`FIX`／`IMPROVE`）**：需求已確定時直接依已確認需求執行，不重新啟動問卷；先確認修改前基線，僅實作本次明確要求的範圍，保留既有功能與資料相容性；完成必要測試、操作驗證與 `git diff` 檢查。
- **C. 發布／結案任務（`RELEASE`／`HANDOFF`）**：執行 Release Gate 與跨 Agent 交接；UI 美化不得自動成為發布前必要項目，Release Gate 已通過時不因更漂亮的介面延後發布。
- **D. 需求探索／產品決策任務（整合於 `EVALUATE` 產品探索模式）**：
  - 流程：讀取現況 ➜ 分析產品 ➜ 動態訪談 ➜ 使用者回答 ➜ 研究及比較方案 ➜ 收斂需求 ➜ 產出決策摘要（詳見 `references/project-product-assessment.md` 第 5 節）。
  - 預設唯讀，不修改 Repository、不重構、不 Commit、不 Push，且與 A（檢查）、B（修正／改善）、C（發布／結案）任務保持明確區分。
