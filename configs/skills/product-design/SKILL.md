# 產品設計與 UI/UX 審查 (Product Design Skill)

> 設計不是裝飾，而是消除「使用者」與「所需結果」之間的摩擦。

## 1. LiangHao 工作區對齊原則（最高優先）

1. **語言**：所有分析、設計規格與介面文案一律使用標準台灣繁體中文。
2. **探索與執行分流**：
   - 使用者要求「規劃產品／問卷引導／重新評估專案」且方向未定時，先依 `lianghao-development` 之 `references/project-product-assessment.md` 第 5 節進入唯讀引導探索，不寫入程式碼。
   - 需求已明確或要求直接實作、修改、修復時，依既有架構直接執行，不阻斷於問卷。
3. **系統字型與離線優先**：Windows 桌面工具、免安裝 Portable、公務／行政系統優先採用系統字型堆疊（`Segoe UI`, `Microsoft JhengHei UI`, `system-ui`），不強制引入外部 Web Fonts。
4. **規模與門檻裁剪**：完整產品／重度互動依循全套 8 種元件狀態與反應指標；小型內部工具與局部修復依 `windows-tool-ux` 實測體感與最小修改原則按需套用，不因美化延後發布。
5. **案例比較與反制式 AI 介面（依 `lianghao-development` `references/agent-execution.md` 第 3、4 節）**：
   - 全新 UI、整體改版或重大流程調整前，先理解用途並比較 **2～3 個可查證案例**（成熟軟體、GitHub 開源 UI 或遊戲介面），註明來源與參考原因；一般局部修復不強制研究。
   - 未指定風格時依產品性質自主選型，避免無理由堆疊圓角卡片、白底紫漸層、裝飾陰影、無用浮動面板或過多彩色圖示。
   - 工具軟體套用遊戲風格 UI 時須分開選定「遊戲類型」與「美術風格」，嚴禁自行加入等級／經驗值／成就／虛擬貨幣或把日常操作改成難懂術語；僅要求 UI 預覽圖時應依實際功能生圖且不修改正式程式。

## 2. 回應模式分流 (Quick vs Full Mode)

- **Quick Mode**（單一元件、局部檢查、操作診斷或快問）：直接對話式切入問題與修正建議，於內部套用所有設計原則，不輸出長篇八段模板與清單。
- **Full Mode**（全新應用概念、跨頁面流程或架構級改版）：先補齊四個核心脈絡（主要使用者、核心任務、最高風險時刻、完成判準——可從 Repo 推斷者不反問），再依 `references/ai-interface-patterns.md` 第 2 節之 8 段式結構輸出。

## 3. 核心設計紅線摘要

- **資訊架構 (IA)**：嚴守 **Identity（定位）➜ Status（狀態）➜ Action（操作）➜ Context（脈絡）** 順序；主導覽上限 5–7 項；低於 30% 使用者在前 30 秒需要的功能預設收進抽屜／彈窗。
- **互動與狀態完整性**：重要元件視需求設計 **Empty / Loading / Partial / Populated / Error / Disabled / Read-only / Overflow** 狀態；錯誤須具體指出復原路徑且不得遺失使用者草稿；觸控熱區 ≥ **44×44 px**；危險／不可逆操作須預覽或白話確認。
- **視覺與 Design Tokens**：先定語意角色色再定色票（品牌色 ≤ 3），文字對比度 ≥ **4.5:1**；採 Base-8 間距與一致字級（≤ 6 階）；尊重 `prefers-reduced-motion`；淺色為預設，深色僅在情境明確（開發／監控／影音／高密度專業介面）時採用。
- **AI 互動（如有）**：標示推論來源與信心層級、串流預留空間並允許隨時中斷、高風險動作須人類確認、模型失敗時核心功能須能優雅降級。
- **文案**：按鈕寫使用者意圖（「儲存變更」「刪除帳號」），不用「確定／送出」；不用 Placeholder 取代欄位標籤。
