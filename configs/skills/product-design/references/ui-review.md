# UI 審查與驗收

## 1. 建立可比較基線

先確認本次範圍、主要使用者任務、支援平台／尺寸與完成判準；從現有專案推斷，不為局部修改另開問卷。記錄版本（含未提交差異）、頁面／視窗、資料與狀態、視窗尺寸、縮放、主題與工具。可執行時先取得截圖並走過核心操作；只有原始碼或舊圖時註明「靜態審查」，核對圖與目前版本是否一致，不將推測列為已重現缺陷。

## 2. 檢查與收斂

- 先檢查任務入口、狀態、主要操作與錯誤復原，再檢查視覺細節；沿用 `design-standards.md`，不另製相同清單。
- 比較受影響畫面與相鄰流程的同角色元件：字級／行高、間距／對齊、語意色、圖示線條與尺寸、按鈕層級、焦點／停用／錯誤狀態、用詞。優先沿用既有 token 與共用元件；單一例外不強制抽象，不為一致性更換框架或消除產品特色。
- 表格／圖表／流程圖依內容檢查文字、圖例與連線是否重疊或被裁切；資訊過密才拆概覽與細節，不套用第三方固定節點上限。寬表可在有標示的區域內捲動，不應迫使整頁橫向捲動或隱藏核心操作。
- 動畫只用於必要回饋，檢查減少動態效果時仍可讀取內容、辨識狀態。未量測不得宣稱效能提升。

## 3. 缺陷紀錄與優先順序

分類沿用 [Agent 執行規範](../../lianghao-development/references/agent-execution.md) 第 2 節，不引入另一套 P0–P3 分數。

每項缺陷記錄：識別碼、位置、重現條件、預期／實際、畫面或操作證據、任務影響、分類、最小修正建議與複驗結果。多個畫面同根因合併記錄，列出受影響範圍；區分「已重現」「靜態疑點」「風格建議」。

- 核心操作無法完成、誤導狀態造成資料損失，依影響列阻斷性；重要但可繞過的已重現裁切、鍵盤或復原問題列重要。
- 純圓角、配色或動畫偏好列改善建議，不升格為發布門檻。同級先處理影響核心任務、涵蓋使用者較多者；未取得頻率或使用率資料時標示未知，不杜撰數字。

## 4. 修改後複驗與交付

以相同資料、狀態、尺寸、縮放、主題及工具重走核心路徑，並對照前後截圖；若條件不同，記錄原因與不可比較之處。改前先記錄受影響按鈕的事件、表單送出、連結／下載目的地與必要狀態，改後逐項核對；不能只保留外觀而遺失接線。確認操作步驟、資料與功能未退化，檢查修改引起的相鄰元件影響。像素差異僅是線索，不代表 UX 成敗。

網頁尺寸、縮放與操作證據依 [webapp-testing](../../webapp-testing/SKILL.md)；Windows 桌面依 [windows-tool-ux 相容性清單](../../windows-tool-ux/checklists/windows-compatibility.md)。沒有執行工具時不得把新增提示詞描述成自動截圖、幾何檢測或通過驗收。

交付只需列受影響範圍、已修正缺陷、前後證據與條件、通過／失敗／略過／待本機驗證及剩餘風險；沿用專案現有交接／測試報告，不強制新增文件。目標與必要檢查達成後停止，不追逐主觀滿分。
